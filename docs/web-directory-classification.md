## Proposed safest move order for frontend extraction

1. **Do not migrate generated artifacts** (`.next`, `out`, `node_modules`, `next-env.d.ts`, `.DS_Store`); treat as disposable/regenerated.  
2. **Move clearly frontend source/config as a unit**: `app`, `components`, `package.json`, `package-lock.json`, `next.config.ts`, `tsconfig.json`, `eslint.config.mjs`.  
3. **Resolve ambiguity before moving**: decide ownership/contract for `lib` and `public` (especially `public/reports`).  
4. **After ownership decision**, move `lib` and `public` if they remain frontend-owned.  
5. **Finalize docs/ignore cleanup** for `.gitignore` and `README.md`.

## Risks / ambiguities to resolve first

- `web/lib/reports-data.ts` and `web/public/reports` suggest the frontend directly reads report JSON at build-time; if that data is later pipeline-generated/shared, ownership must be explicit before moving.
- Moving frontend source without coordinated path updates can break import aliases and data file resolution.
- Build artifacts in `web/` can obscure what actually needs migration; safest approach is to ignore/remove them from migration scope.
